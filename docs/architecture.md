# 架构约束

红叶镇会逐步加入畜牧、加工、合成、抽卡和社交系统。首版规模很小，但以下边界从一开始保持稳定。

伙伴、主角天赋、逐格生产和品质公式见 [`game-design-foundations.md`](game-design-foundations.md)。本文件描述代码与数据边界，设计文档描述这些边界承载的游戏规则。

## 分层

```text
Web / QQ / 后台任务
        ↓
Application services（完整用例和事务边界）
        ↓
Domain（资源、成长、时间结算规则）
        ↓
Repository ports
        ↓
Redis / 测试内存实现
```

Web 和 QQ 不能直接修改玩家对象。一次购买、种植、收获、制作或抽卡必须是一个 application service 用例，并由 repository 的原子 `update` 提交。

## 身份

- `player_id` 是游戏内部稳定 UUID。
- 水鱼 OAuth `sub` 与 `player_id` 是严格一对一关系，由 Redis 原子创建脚本保证。
- QQ 身份使用 `(adapter, bot_id, openid)`，不能假定官方 Bot 可以获得 QQ 号。
- QQ 绑定只用于寻找已有角色，不能创建第二个角色。
- 红叶镇使用独立 Cookie 和 JWT audience，不能接受 Aether 或 fishdown 会话。

## 时间系统

不为每块土地建立常驻定时任务。状态保存开始时间和结束时间，在读取或操作时以服务器时钟懒结算：

- 作物：`planted_at`、`ready_at`
- 体力：已存体力、`stamina_updated_at`、恢复间隔
- 未来畜牧与加工队列沿用相同时间段模型

客户端倒计时只是显示，收获资格和离线收益始终由服务器判断。

每个生产格独立持有任务和开工快照。同一产业的不同土地或设备可以执行不同内容，并驻场零至两名伙伴。任务同时引用本格负责人和实际提供空间效果的支援伙伴；被任意进行中任务引用的伙伴不能改变站位，到达相关任务的完成时间后自动解除引用，不依赖玩家领取。任务开始后的升级、突破、天赋和站位变化只影响新任务。

农田的空间关系由邻接图描述，首版界面表现为上下左右四邻接；其他设施可以提供不同拓扑。开工时将生效的相邻或定向效果及来源写入快照，进行中不动态重算。repository 的原子 `update` 必须同时校验伙伴站位、产业总编制、所有锁定引用和任务创建，避免一个伙伴并发出现在多个位置。

## 内容与收益曲线

`data/game.json` 是首版内容入口，包含等级累计经验、土地与采集点、体力上限、解锁项、产业规则、天赋节点、商品、生产任务产量、品质和价格。农作和采集产业分别配置主角基础能力、基础伙伴编制、伙伴有效等级上限和单格协作者位置；每种作物与采集任务配置独立的时间难度、产量、四个严格递增的品质阈值、分布宽度、奇迹资格与概率上限。全局品质表配置五档名称和售价倍率。配置由 Pydantic 在启动与测试时验证引用完整性、阈值顺序、概率上限与五档完整性。

`data/partners.json` 独立保存伙伴卡片配置，避免后台维护伙伴时重写经济与作物数据。伙伴配置由 Pydantic 校验稳定 ID、产业倾向、1/60 级能力、成长曲线、特性代号、突破插画比例，以及三个突破阶段各自的头像裁剪边界。后台写入使用临时文件原子替换；插画上传时复核管理员选择的 9:16 裁剪框，限制输出为最高 1080×1920，统一转码为 WebP，再通过宿主提供的统一 CDN provider 上传。插画和头像使用同一个可视化裁剪组件，前端只提交坐标，后端仍负责最终边界校验。应用只保存 object key，不增加本地原图直出路由。

玩家存档中的 `owned_partners` 只保存 `partner_id`、等级、突破阶段和获得时间，并由领域模型拒绝重复 ID。schema v3 会在读取旧存档时把 `owned_spirits[].spirit_id` 迁移为 `owned_partners[].partner_id`；schema v4 为生产格增加 `assigned_partner_ids` 和 `task_snapshot`；schema v5 把库存改为 `item_id → quality → quantity`；schema v6 增加采集点状态与已点亮天赋节点。旧的可品质化产物在首次服务结算时归入普通品质，不支持品质的种子与材料保留无品质的 `0` 桶。下一次原子更新会写回最新结构。领域模型同时拒绝同一伙伴跨农田和采集点重复派驻，以及生产格引用未持有伙伴。玩家快照在读取时把仓库状态与当前 `data/partners.json` 合并，因此内容热更新无需重写全部玩家存档。管理员搜索玩家和发放伙伴必须经过 application service 与 repository 原子 `update`，后端负责再次校验伙伴存在及唯一持有，不能把一致性责任留给管理前端。

农作与采集开工共用 `A = 主角对应产业能力 + Σ 驻场伙伴有效能力` 和收益递减时间公式生成 `ProductionTaskSnapshot`。采集服务额外要求恰好一名具有采集倾向的伙伴，并用“基础采集编制 + 已点亮采集天赋加成”校验派驻上限。快照固定记录规则版本、生产格、直接伙伴、预留支援来源、伙伴等级与能力、已展开效果、基础/最终时长、产量区间、经验和完整品质概率参数。成熟后的首次读取在 repository 原子 `update` 中生成并保存单一 `task_result`，整批产物共享一次品质判定；领取只负责把结果转入对应品质库存。成熟后锁定引用按服务器时间失效；是否领取不影响伙伴移动资格。

新的系统应遵守以下规则：

1. 静态内容使用稳定 ID，不把显示名称写进玩家存档。
2. 成本和奖励通过领域经济函数结算，不在路由或前端直接加减。
3. 解锁条件由等级/功能键配置驱动，不散落成页面特判。
4. 玩家存档保留 `schema_version`，改变结构时先增加迁移函数和旧存档测试。
5. 调次数值时测试单位时间净收益、回本时间和体力效率，而不只测试单次结果。
6. 生产任务保存规则版本与结算快照，进行中的任务不能被配置热更新改变结果。
7. 伙伴特性保存稳定效果 ID、目标选择器和叠加组；实际命中的空间效果在开工时展开到任务快照。
8. 玩家只持有伙伴的稳定 ID 和培养状态；静态卡片信息不复制进存档，同一玩家的伙伴 ID 必须唯一。

建议对每个阶段维护三条基准曲线：金币/小时、经验/小时、体力价值。畜牧和加工应提高资金利用率或离线时长，而不是在同等级无条件碾压种植。

## 后续模块

- `livestock`：畜栏容量、饲料成本、产出周期和动物成长。
- `crafting`：配方输入、生产队列、设施等级和批量结算。
- `gacha`：卡池版本、服务器随机源、保底计数、抽取历史和幂等请求 ID。
- `unlocks`：统一评估等级、前置任务和设施条件。
- `ledger`：对抽卡、付费货币及高价值交易记录不可变流水。

抽卡实现前必须先落地服务器端随机、保底状态原子更新、结果流水和重复请求保护；前端动画不能参与决定结果。
